## 一、缺陷清单

### 🔴 P0 — F1：模板库品牌约束闭环断裂（Logo 主色 / 禁用词在生产 UI 路径上永不生效）

**现象**：FR-1.3 最有价值的两个字段（`logoColor` / `bannedWords`）**存得进、套不出、提不了**。

| 环节 | 状态 | 证据 |
|------|------|------|
| 后端 schema | ✅ 支持 | `schemas.js` L22-23、L33-34 |
| Provider 注入 | ✅ 支持 | `providers.js` L108/L203/L204/L259/L282 |
| 模板存储 | ✅ 支持 | `templates.js` PRESETS 均带 logoColor/bannedWords |
| 前端采集 | ❌ **无** | `saveCurrentAsTemplate()` 无 logoColor，`bannedWords` 硬编码 `[]` |
| 前端套用 | ❌ **无** | `applyTemplate()` 仅回填 brandName/productName/coreSellingPoint/defaultLanguage/defaultTone |
| 前端提交 | ❌ **无** | `submitBrief()` 构造的 brief 不含这两个字段 |
| `templateToBrief()` | ❌ **死代码** | 全仓 `grep` 仅命中定义处 `templates.js:107`，**零调用** |

**后果**：套用模板后 brief 无 `logoColor`/`bannedWords` → `providers.js` 中 `if (brief.logoColor)` / `if (brief.bannedWords?.length)` **恒为假** → 品牌主色与禁用词约束永远不触发。除非手工 `curl /api/generate` 自行带字段，否则该能力对终端用户不存在。

**证据**：`grep -c "logoColor\|bannedWords" public/index.html` = **2**，且两处均在 `loadTemplates()` 的列表展示（L171），**非表单输入/回填/提交**。

**与 PRD 的冲突**：PRD §4 用户故事明确点名「作为市场运营，我想保存一套品牌模板（**Logo 色、口号、禁用词**），下次一键套用，保证调性统一」——当前实现未满足。

### 🟠 P1 — F2：预设模板可被客户端覆盖并删除（完整性破坏）

`POST /api/templates` 直接 `saveTemplate(req.body)`，而 `BrandTemplateSchema` 的 `id` / `isPreset` **均为客户端可控字段**。

**实测复现**：
```
POST /api/templates  { id:"preset-tech", name:"伪造覆盖", isPreset:false }
→ 覆盖后 isPreset=false
→ DELETE /api/templates/preset-tech 结果=true
→ 预设仍存在? false          ← 预设被永久删除
```
**连锁**：预设删光后 `templates.json` 变 `[]`，重启时 `hydrate()` 因 `fs.existsSync` 为真走「读文件」分支，**不会重新注入预置** → 5 个预设永久消失。

---

### 🟠 P1 — F3：可伪造 `isPreset` 造出永不可删僵尸模板

**实测复现**：
```
POST /api/templates { name:"僵尸模板", isPreset:true }
→ 创建 isPreset=true → 可删? false      ← 永久占列表、无法清理
```

---

### 🟠 P1 — F4：`PROMO_PERSIST=0` 时预置模板数为 0，FR-1.3 失效

`hydrate()` 首行 `if (!persistEnabled()) return;` —— 持久化开关**直接吞掉预置注入**（`templates.js` L49）。

**实测复现**：
```
PERSIST=0 预置数=0
PERSIST=1 预置数=5
```
「首次启动自动写入 ≤5 个预置模板」是 **FR-1.3 的产品行为**，不应被持久化开关劫持。生产默认 `PROMO_PERSIST=1` 故主路径不炸，但任何关持久化的部署（含未来测试态）都会让模板库变空壳。

---

### 🟡 P2 — F5：`PUT /api/templates/:id` 部分更新丢字段

实现为 `saveTemplate({ ...req.body, id })` —— **全量替换而非 merge**。

**实测复现**：
```
全量存 { name:"全量模板", logoColor:"#0ea5e9", industry:"科技", defaultLanguage:"en" }
PUT { name:"只改名" }
→ logoColor=undefined  industry=undefined  lang=zh-CN   ← 静默丢失
```
**注意**：现有测试 `templates.test.mjs:33` 的 `saveTemplate({ id, name:"改名" })` 只断言 `name`，**掩盖了该缺陷**（该测试对「全量替换」与「merge」两种语义都会通过）。

---

### 🟡 P2 — F6：`logoColor` 无格式校验

schema 仅 `z.string().max(20)`。DEMO 路径 `c1 = brief.logoColor` 直接进 SVG 填充属性。
- 安全性：`encodeSVG` 对整体 `encodeURIComponent`，`<img src="data:...">` 中 SVG 脚本不执行 → **非 XSS**
- 可用性：任意字符串可破坏 SVG 结构导致图裂（低危但真实）

## 三、文档漂移（PRD §16.11 自我描述不准确）

本轮评审发现**我上一轮撰写的 §16.11 存在不准确表述**，需随修复一并订正：

1. **§16.11.4 契约**：写「`applyTemplate(t)` 回填 品牌名/产品名/卖点/语言/默认调性」——**未提 logoColor/bannedWords**，等于把 F1 缺陷写成了正式契约。
2. **§16.11.4 契约**：写「`templateToBrief(t)` 供后端复用」——实为**零调用死代码**。
3. **§16.11.6 DoD**：「套用回填 Brief 表单」措辞含糊，致使 F1 通过验收。应明确为「回填含 logoColor/bannedWords 在内的全部模板字段」。

## 四、修复建议（按优先级）

### 必修（P0/P1）
1. **F1 接通闭环**（三处）：
   - 表单增 `logoColor`（color input）与 `bannedWords`（逗号分隔文本）输入
   - `applyTemplate()` 回填两者；`saveCurrentAsTemplate()` 采集两者
   - `submitBrief()` 带上两者
   - 并让 `templateToBrief()` 真正被使用（或删除，二者择一，不留死代码）
2. **F2/F3 服务端剥离客户端可控字段**：`POST` 强制 `isPreset:false` 且忽略客户端传入的 `id`（或校验 id 非 `preset-*` 前缀）；`PUT` 对已存在预设强制保留 `isPreset:true` 且**禁止改名以外破坏**；`DELETE` 判定改用「id 前缀 `preset-`」而非仅 `t.isPreset` 标志位。
3. **F4 解耦预置注入与持久化开关**：`hydrate()` 先无条件注入 PRESETS（内存），再按 `persistEnabled()` 决定是否读盘/写盘。

### 建议修（P2）
4. **F5** `PUT` 改为 merge：`saveTemplate({ ...existing, ...req.body, id })`。
5. **F6** `logoColor` 加 hex 校验：`/^#([0-9a-fA-F]{3}|[0-9a-fA-F]{6})$/`。

### 补齐测试（与修复同批）
6. 增 F1 端到端用例（套用模板 → `submitBrief` → 断言 brief 含 logoColor/bannedWords → provider prompt 含注入）
7. 增 F2/F3 防护用例（伪造 id/isPreset 应被拒）
8. 增 F4 用例（`PROMO_PERSIST=0` 下预置仍为 5）
9. 增 F5 用例（PUT 部分字段后其余字段保留）
